# Supabase: подключение аккаунтов Luna Voice

Этап 5, 17 сентября 2026. Выбран PostgreSQL в Supabase, вход с паролем и Google OAuth. Приложение использует публичный API с правилами доступа в БД. Пароли обрабатывает Supabase Auth. Настройка и переход со старого входа по коду: [AUTH_SETUP.md](AUTH_SETUP.md).

## 1. Создать проект и выполнить SQL

Создайте проект в Supabase, выбрав регион ближе к пользователям. Откройте **SQL Editor → New query**.

Скопируйте **всё содержимое [SUPABASE_SETUP.sql](../SUPABASE_SETUP.sql)** из корня проекта и нажмите **Run**. Он содержит миграции 001 и 002. Для уже созданной базы выполните только [обновление Auth](../SUPABASE_AUTH_UPDATE.sql). Его можно выполнить повторно: существующая история не удаляется.

Скрипт создаёт таблицу записей, журнал обработанных операций, RLS и функции синхронизации/удаления аккаунта. Не нужно вручную создавать пользователей или заполнять фиктивные результаты. Аккаунты создаёт Supabase Auth при входе, а история появляется после практики или переноса гостевых данных. Каталог упражнений остаётся версионированными данными приложения.

## 2. Подключить приложение

Скопируйте `.env.example` в `.env.local` в корне и заполните:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_KEY
```

URL и **Publishable key** доступны в настройках проекта Supabase. Допустим старый публичный `anon` key. Secret/service_role key здесь не нужен и не должен попадать в приложение. `.env.local` исключён из Git.

Перезапустите `npm run dev`. Для production пересоберите приложение: публичные переменные встраиваются при сборке. Без этих параметров гостевой режим продолжает работать, а экран входа сообщает, что облачное подключение не настроено.

## 3. Настроить вход

Включите Email и Google, добавьте адреса возврата и настройте письма подтверждения/восстановления по [AUTH_SETUP.md](AUTH_SETUP.md). Старые аккаунты без пароля используют «Забыли пароль?». Гостевая история не переносится автоматически после входа.

## 4. Проверка после подключения

Проверьте вход паролем и Google, подтверждение/восстановление, перенос гостевой истории, синхронизацию на двух устройствах и офлайн-очередь. На отдельном тестовом аккаунте проверьте удаление после свежего входа. Настройку реального Supabase/Google и доставку писем нужно проверять отдельно от имитации API в автотестах.

## Схема и защита данных

`auth.users` принадлежит Supabase Auth. `public.voice_records` содержит составной ключ `(owner_id, kind, id)`:

| kind | Содержимое |
|---|---|
| attempt | Снимок попытки, параметры и результаты нот |
| session | Очередь упражнения и связи с попытками |
| setting | Одно поле настроек; темп хранится отдельно для каждого упражнения |
| favorite | Состояние избранного для упражнения |
| profile | Отображаемое имя |

Это версионированные снимки уже существующей локальной модели. Подробные показатели нот хранятся в JSONB попытки: не нужно создавать отдельную серверную запись для каждого кадра или ноты. Когда появятся серверные аналитические отчёты, можно добавить SQL-представления или отдельные таблицы без изменения исходных версий результатов.

RLS разрешает пользователю читать только свои строки. Прямые insert/update/delete клиенту запрещены. RPC `voice_apply` берёт владельца из `auth.uid()`, проверяет существование аккаунта, допустимость операции и размер данных. Переданный клиентом owner_id не используется. Функции с повышенными правами имеют фиксированный пустой search_path и закрыты для anon. Приватный журнал операций недоступен через клиентский API.

`voice_delete_account` принимает **ноль параметров**, удаляет только текущего пользователя и требует вход паролем, OAuth или старым OTP в последние 15 минут по подписанному claim `amr`. Удаление каскадом очищает записи и журнал. Старый JWT удалённого пользователя не позволяет создать данные заново. Резервные копии могут содержать удалённые записи до истечения срока хранения.

Аудиозапись и линия голоса не отправляются. На сервер передаются производные результаты и параметры попытки, включая ID микрофона и поправку задержки для корректного сравнения. Сами настройки чувствительности/задержки для следующего занятия остаются локальными для устройства. Недавние упражнения также остаются локальным списком.

## Офлайн, конфликты и перенос

- Гостевая база: `lunavoice-history`. Аккаунт: `lunavoice-history-<user-id>`. Выход переключает пространство данных, не смешивая их. Кэш аккаунта и неотправленные операции остаются на устройстве до следующего входа; очистка данных сайта удалит их.
- IndexedDB v3 добавляет `outbox`. Изменение и операция отправки записываются одной транзакцией. Если локальная запись не удалась, показывается предупреждение; закрытие вкладки до восстановления хранения может потерять несохранённые изменения.
- Каждая операция имеет UUID. Сервер сохраняет квитанцию; потеря ответа и повтор запроса не повторяют действие. Вкладки одного аккаунта согласуют отправку через Web Locks, когда API доступно; серверная идемпотентность действует независимо от него.
- Синхронизация запускается после локальной записи, при возврате сети/фокуса и раз в 15 секунд. За проход отправляются до 50 операций; остаток остаётся в очереди. Чтение идёт страницами по 500 записей, включая пометки удаления. Это рассчитано на объём закрытой беты; для больших историй следующим шагом будет журнал изменений и инкрементальная загрузка.
- Параметры разрешают конфликт по **последней операции, принятой сервером**, отдельно для каждого поля/темпа/элемента избранного. Офлайн-изменение может заменить более раннее серверное значение после подключения.
- Первая принятая финальная версия попытки неизменяема. Старый промежуточный снимок не заменяет завершённую попытку. Повтор упражнения всегда получает новый ID.
- Удаление оставляет tombstone — пометку, которая не позволяет старому устройству воскресить запись. Очистка истории удаляет все попытки, известные серверу на момент обработки; ещё не отправленная новая попытка другого устройства может появиться позднее. Пометки и квитанции не чистятся автоматически, поскольку иначе старые очереди могут повторить удалённые действия.
- Гостевой перенос копирует историю и избранное, не удаляя оригинал и не заменяя настройки аккаунта. Повторный перенос не создаёт дублей. Историю можно экспортировать отдельно до переноса.

## Миграции и резервные копии

Схема ведётся в `supabase/migrations`. Следующие изменения оформляйте новой миграцией; не редактируйте задним числом уже применённую схему проекта. Первоначальный скрипт допускает повторное выполнение для установки текущей версии функций и политик.

На Free автоматические резервные копии не включены. Для данных беты настройте регулярный защищённый экспорт или используйте Pro с ежедневными резервными копиями. Это настройка размещения, SQL её не включает. [Резервные копии Supabase](https://supabase.com/docs/guides/platform/backups).

Для отдельной логической копии данных приложения используйте PostgreSQL `pg_dump` с direct/session-pooler соединением из Supabase Dashboard (не transaction pooler):

```sh
pg_dump "$LUNAVOICE_DATABASE_URL" --format=custom \
  --table=public.voice_records --table=voice_private.receipts \
  --file=lunavoice-data.dump
```

Храните файл и URL с паролем вне репозитория, в защищённом хранилище. Такая копия **не включает пользователей Auth**, настройки SMTP и ключи проекта. Для полного восстановления используйте резервную копию проекта либо документированный экспорт/восстановление Supabase. Простого переноса этих двух таблиц в новый проект без исходных auth.users недостаточно из-за внешних ключей.

Проверять восстановление нужно в отдельном тестовом проекте, со схемой, соответствующими пользователями и последующей проверкой RLS, количества записей, квитанций и входа. После восстановления старой копии отдельно учтите удаления, произошедшие после её даты: восстановление не должно незаметно вернуть удалённые аккаунты.

Локальная проверка `npm run test:database` создаёт временные базы в PostgreSQL на 127.0.0.1:55439 (можно задать `LUNAVOICE_TEST_PG_PORT`), проверяет SQL и полный цикл pg_dump/pg_restore с тестовыми пользователями. Она не подключается к облаку.

## Автоматические браузерные проверки

Для тестов аккаунта соберите приложение с безопасным фиктивным адресом:

```sh
NEXT_PUBLIC_SUPABASE_URL=https://lunavoice-test.supabase.co \
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_test \
npm run build -- --webpack
LUNAVOICE_CLOUD_TESTS=1 npm run test:browser
```

Без `LUNAVOICE_CLOUD_TESTS=1` сценарии аккаунта пропускаются, остальные проверки работают в гостевой сборке. Тесты `account.spec.mjs` перехватывают все запросы к этому адресу; писем и внешних аккаунтов не создают. После проверки пересоберите с настоящими параметрами либо без параметров для гостевой версии. Не публикуйте тестовую сборку.
